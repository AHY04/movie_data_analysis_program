# TMDB 영화 데이터 분석 프로젝트

## 1. 프로젝트 의의
Python을 활용해 TMDB API에서 영화 데이터를 수집하여 CSV파일을 생성하고, 정규화된 MySQL 스키마로 적재한 뒤, 다대다 관계를 포함한 분석 쿼리를 작성하여 데이터를 시각화 한다.

- API -> CSV -> MySQL까지 데이터를 적재하는 과정 전체를 경험
- 단순 데이터 수집이 아닌 정규화, 적재, 분석, 데이터 시각화까지 완전한 데이터 파이프라인 설계 및 구현
- JOIN, GROUP BY등 SQL을 활용한 분석 쿼리 작성 능력 향상


## 2. 단계별 진행 내용 및 유의사항

### 1단계 - TMDB API 영화 데이터 수집
- 'get_popular_movies()'함수를 선언하여 인기 영화 목록 가져오기
- 'get_movie_detail()'함수를 선언하여 영화 상세 정보 가져오기
- 수집 항목: 영화 기본 정보, 장르, 감독

*유의사항
- 'append_to_response="credits"'로 감독 정보까지 수집
- API 호출 제한(RATE LIMIT) 주의
- TMDP API사이트에서 파라미터 이름, 구조 등과 같은 서버규약 확인

### 2단계 - CSV파일 생성
- 생성파일:
- movies_raw.csv
- genres.csv
- directors.csv
- movie_genres.csv
- movie_directors.csv

*유의사항
- 반복문 활용으로 인해 'genres.csv'와 'directors.csv'에 중복된 데이터가 저장되는데, 이를 제거하지 않으면 PK 충돌로 인해 MySQL에 적재 불가
- 따라서 'genres.csv'는 'genre_id'기준, 'directors.csv'는 'director_id'기준으로 중복 제거 필요
- CSV파일 생성 후, 저장 경로 및 파일 존재 여부 확인

### 3단계 - MySQL 테이블 생성
- 테이블 설계:
- 'movies' (PK: movie_id)
- 'genres' (PK: genre_id)
- 'directors' (PK: director_id)
- 'movie_genres' (PK: movie_id+genre_id, FK: movie_id(movies), genre_id(genres))
- 'movie_directors' (PK: movie_id+director_id, FK: movie_id(movies), director_id(directors))

*유의사항
- CSV파일의 컬럼과 DB 컬럼의 순서가 일치하는지 확인
- UTF-8 설정 필수(한글 영화 제목 대응)

### 4단계 - CSV->MySQL 적재
- pandas + mysql.connector 사용
- 적재 순서: movies -> genres -> directors -> movie_genres -> movie_directors

*유의사항
- 부모 테이블 먼저 적재 후 자식 테이블 적재(FK 제약으로 인해 부모 테이블이 없으면 INSERT 실패)
- 실행 후 데이터가 잘 적재되었는지 확인

### 5단계 - SQL분석
- 다대다 JOIN을 활용한 분석 쿼리 작성:
- 감독별 영화 제작량 TOP10
- 감독별 평균 영화 평점 TOP10
- 영화 평점 TOP10
- 장르별 영화 비율
- 장르별 평균 평점

*유의사항
- AVG, COUNT 사용 시 데이터 중복으로 인한 부적절한 집계가능성 검토


## 3. 도출 가능한 결론

- 감독별 영화 제작량: 감독별 영화 수 통계를 통해 활동적인 감독 파악 가능

- 감독별 평균 영화 평점: 감독별 영화 평점을 비교함으로써 각 감독의 인기도 및 영화 퀄리티 비교 가능

- 영화 평점: 인기있는 영화들의 목록 파악 및 평점 비교 가능

- 장르별 영화 비율: 각 장르별로 제작된 영화 수 통계를 통해 활발하게 제작되고 있는 장르 파악 가능

- 장르별 평균 평점: 액션, 코미디 등 각 장르의 평점 및 인기도 비교 가능


## 4. 프로젝트를 통해 배운 점

### 1) 다대다 관계 설계의 중요성
영화-장르, 영화-감독 관계를 테이블로 분리하기 위해 다양한 시도를 해 보았다. 설계의 편의성을 위해서 테이블의 수를 최대한 줄여도 보고, 
컬럼을 추가하며 테이블끼리 합쳐보기도 하면서 데이터베이스 구조를 설계할 때는 단순히 실용성만이 아니라 데이터 무결성 및 설계 이후의 분석 확장성까지 고려해야함을 알 수 있었다. 단순 컬럼 추가가 아닌 중간 테이블 설계가 향후 데이터 확장성과 분석 정확도에 큰 영향을 끼친다는 사실을 배움으로써 정규화된 데이터베이스 구조의 필요성을 체감하였다.

### 2) 집계 함수에 대한 이해도
SQL에서 집계 함수는 원본 테이블이 아니라 JOIN 이후의 결과로 나오는 집합을 기준으로 동작한다는 점을 알게 되었다. 따라서 COUNT, AVG등과 같은 집계 함수를 사용할 때는 JOIN 이후의 중복된 값에 의해 의도와는 전혀 다른 집계 결과가 도출될 수 있으므로, DISTINCT 또는 서브쿼리가 필요한 상황과 그 이유를 명확히 알 수 있었다.

### 3) 데이터 파이프라인 설계 경험
프로젝트 전에는 단순히 SQL로 주어진 데이터를 분석하는 능력만 갖추고 있었으나, 본 프로젝트에서 API 호출 -> CSV 저장 -> MySQL 적재 -> SQL 분석 -> 시각화까지 데이터 처리의 전 과정을 직접 구현해보며 원하는 데이터를 수집하여 가공해보는 경험과 데이터 흐름 전체를 이해하는 경험을 할 수 있었다.

### 4) 분석 결과 시각화의 중요성
SQL 분석 결과를 Python의 matplotlib을 활용해 시각화하면서 데이터 분석에서 결과를 이해하기 쉽게 전달하는 것의 중요성을 체감했다. 단순히 표를 통해 숫자 및 통계수치만 나열하는 것보다 그래프를 통해 시각적으로 표현하는 것이 전달력이 뛰어나고 효과적임을 배웠다.


## 5. 한계점 및 개선 방향

### 1) 데이터 범위의 한계
혼자서 직접 데이터를 수집하고 분석해보는 것이 처음이었기에 본 프로젝트에서는 TMDB의 인기 영화 데이터의 일부만을 수집하였다. 따라서 전체 영화 데이터를 활용하지 못해 정확한 결과를 도출하지 못한 점이 한계로 남았다.

*개선 방향
- 페이지 수 확장 또는 인기 영화 목록이 아닌 다른 엔드포인트(현재 상영중인 영화 등) 활용
- 개봉 연도별 영화 트렌드 분석을 위해 장기간의 데이터 수집

### 2) JOIN 확장 시 집계 오류 가능성
본 프로젝트에서는 영화-장르 또는 영화-감독 관계만 JOIN했기 때문에 JOIN 이후에도 중복되는 데이터가 발생하지 않아 따로 서브쿼리를 사용하지 않았으나, 더 많은 테이블을 추가 JOIN하게 될 경우 하나의 영화가 여러 행으로 확장되어 평균 평점이나 영화 수 등의 집계 값이 왜곡될 수 있다.

*개선 방향
- 서브쿼리 및 DISTINCT를 활용하여 영화별로 row를 정리한 후 집계
- 집계 함수 사용 시 서브쿼리 및 DISTINCT의 필요성을 명확히 구분

### 3) 데이터 품질 관리의 한계
API에서 데이터를 수집하는 과정에서 같은 장르나 같은 감독 정보가 여러 영화에 반복해서 포함되어 있다. 이로 인해 별도의 중복제거가 필수적이므로 본 프로젝트에서는 Python코드에서 중복 제거를 하였으나, 이러한 방식은 코드에만 의존하기 때문에 데이터 품질을 안정적으로 관리하기에는 한계가 있어 보인다.

*개선 방향
- 데이터 저장 전에 이미 존재하는 데이터인지 확인하는 코드 추가
- 테이블을 만들 때 UNIQUE 제약 조건을 적용하여 데이터 중복 저장 예방
